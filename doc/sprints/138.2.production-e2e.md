## 3. Rzeczywisty baseline kodu

Nie budujemy nowego pipeline'u. Obowiązuje istniejący przepływ:

```text
gameplay conflict resolution
  -> canonical territory conflict snapshot: resolved/closed
  -> durable GhostNetwork conflict job
  -> reconcile_parts_with_territories(resolve_conflicts=True)
  -> ghost.part_conflict_resolved
  -> advance_ghostnetwork_endgame_once()
  -> evaluate_network_readiness()
  -> immutable cycle lock
  -> atomic/idempotent transmission
  -> persisted ghost.signal_sent
  -> GhostNarrativePublisher
  -> ghost_narrative_outbox (processor=ollama)
  -> chaos-ollama-worker
  -> accepted candidate albo jawny policy terminal
  -> chaos-narrative-publisher
  -> publication receipt
  -> lifecycle medium record
  -> BlackNet / Googleplex News / Cyberner
```

PM2 14 dodatkowo wywołuje `advance_ghostnetwork_endgame_once()` niezależnie od
jobów terytorialnych, domyślnie co około 2 sekundy. Zapewnia to drugą próbę po
rozwiązaniu blokady oraz recovery stanów `transmitting` i `stabilizing`.

## 4. Kontrakt dokładnego fan-outu `ghost.signal_sent`

Aktualny canonical event `ghost.signal_sent` nie niesie player/clan audience.
Dlatego jego oczekiwany fan-out to dokładnie trzy taski publiczne:

| Audience | Medium | Wymagany wynik |
| --- | --- | --- |
| public | `blacknet` | `published` lub bezpieczny Support fallback |
| public | `googleplex_news` | `published` albo udowodnione `controlled_slot_supersession` |
| public | `cyberner` | `published`; jawny terminal nie cofa gameplayu, ale pozostawia family gate otwarty |

Nie oczekujemy osobnych tasków clan/owner dla samego `signal_sent`. Te audience
mogą wystąpić przy `ghost.part_conflict_resolved` lub `ghost.cycle_locked`, jeśli
canonical event zawiera gracza i klan. Ich oczekiwaną liczbę wylicza policy oraz
`scripts/audit_narrative_e2e.py`, nie ręcznie wpisana stała.

Radio jest jawnie poza fan-outem pierwszej emisji. Brak taska Radio jest zgodny
z kontraktem, a nie utratą publikacji.

Przed zatrzymaniem PM2 17 uruchamiamy jeden proces read-only. Monitor odczytuje
wyłącznie lekkie kolumny stanu, nie otwiera profili ani dużych payloadów JSON.
Pierwszy rekord jest pełnym baseline'em. Potem JSONL otrzymuje wyłącznie zmiany
stanu i heartbeat co 30 sekund. Aktualne kompaktowe podsumowanie jest zapisywane
atomowo po każdej zmianie lub heartbeat, więc pozostaje czytelne również po
zerwaniu SSH.

Monitor obejmuje:

- konflikt S1, cykl, części i ring;
- lock, GhostSignal, Show, ranking i eventy końcowe;
- trzy taski `ghost.signal_sent`, attempts, candidates, receipts i medium records;
- nagrody, konsumpcje, archiwizację części i następny cykl;
- kolejki territory/delta oraz stabilny stan PM2 13/14/17/18;
- pierwsze wystąpienie każdego kamienia milowego testu.

Jednorazowy start, odporny na rozłączenie SSH:

```bash
cd ~/app/chaos

nohup .venv/bin/python scripts/monitor_138_2_signal_e2e.py \
  --db data/game.sqlite3 \
```

Proces nie kończy się przy zamknięciu sesji i nie wymaga kolejnych komend

`doc/audits/` kopiujemy JSONL, summary i stdout. Jeżeli proces został przerwany
bez czystego shutdownu, ten sam zapis można kontynuować przez jawne `--resume`;
bez tej flagi monitor nie nadpisze istniejącego JSONL.

## 9. Failure policy

- brak locka przy nadal aktywnym konflikcie: poprawne fail-closed;
- brak locka po canonical resolution: zachować stan, nie mutować SQL, sprawdzić
  conflict job i readiness następnego ticku;
- `transmitting` z poprawnym lockiem: oczekiwać automatycznego resume;
- `transmitting` bez poprawnego locka: fail-closed, backup i analiza;
- sygnał bez trzech tasków: naprawić persisted-event reconciliation, nie wysyłać
  drugiego sygnału;
- task bez candidate: analizować attempt/retry/Support Layer, nie zmieniać eventu;
- candidate bez receipt: naprawić publisher/replay istniejącego candidate;
- brak publikacji Cybernera nie może cofać gameplayu i musi mieć jawny terminal,
  lecz pełny family PASS pozostaje otwarty do poprawnego lineage istniejącego
  taska; nie wolno tworzyć drugiego sygnału;
- `stabilizing` nie wolno naprawiać przez reaktywację części;
- po każdym nieodwracalnym FAIL zachować pełny postflight i kopię bazy przed
  decyzją o restore.
