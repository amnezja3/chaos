## 3. Clan GhostSignal Score

Przyjęta polityka `ghostsignal-ranking-v2`:

| Kategoria | Pula |
| --- | ---: |
| Node Control | 400 |
| Territory Contribution | 300 |
| Conflict Contribution | 200 |
| Signal Closer | 100 |
| **Razem** | **1000** |

Wagi pochodzą z centralnej policy i są utrwalane w każdym snapshotcie.

- conflict metrics są zamrażane w closure locku jako canonical conflict actions;
- pusta kategoria nie jest redystrybuowana między pozostałe kategorie;
- territory contribution używa powierzchni, a przy zerowej/nieznanej powierzchni
  przechodzi na liczbę skonsumowanych terytoriów;
- punkty dzieli metoda największych reszt, z leksykalnym tie-breakiem ID klanu;
- ranking oraz event `ghost.signal_ranking_created` są idempotentnym elementem
  post-commit i obowiązkowym warunkiem settlementu.

Score nie zastępuje surowych statystyk. UI pokazuje również nodes, RSP,
territories, area, conflicts i closerów.

## 6. Strict preflight

Jeden read-only skrypt, np.:

```text
python scripts/audit_ghostnetwork_endgame_preflight.py \
  --strict --expect entry --backup /ścieżka/do/świeżego-backupu.sqlite3
```

potwierdza:

- dokładnie jeden oczekiwany cykl `active`;
- dla planowanego startu stan 19/20 i jedną część zamykającą;
- 20 katalogowych części, 20 connections, poprawny ring/checksum;
- cztery maszyny oraz przewidywane `4 x 5/5` po ostatniej aktywacji;
- poprawne anchors, territories i territory state versions;
- canonical conflict resolver oraz oczekiwany blocker scenariusza;
- brak locka i signal dla bieżącego cyklu;
- brak starych pending rewards/endgame jobs;
- immutable territory dry-run z listą ID i powodów;
- gotowość show i rankingu;
- komplet wymaganych eventów, mediów, fallbacków i CTA;
- PM2 13, 14, 17 i 18 online bez crash loop;
- krytyczne env, HEAD, SQLite health, wolne miejsce i świeży online backup.

Raportuje co najmniej:

```text
ok
cycle_id
phase
network_complete
ready_after_last_part
closing_part
conflict_blockers[]
machine_progress[]
expected_signal_public_id
expected_next_version
expected_rewards
territory_plan[]
expected_events[]
expected_media[]
```

Bez `ok=true` produkcyjna aktywacja jest zabroniona.

Implementacja: `scripts/audit_ghostnetwork_endgame_preflight.py`. Skrypt nie
aktywuje części, nie rozstrzyga konfliktu i porównuje liczniki watched tables
przed oraz po audycie. Przy obecnym stanie `19/20 + brak konfliktu` strict
preflight ma celowo zwrócić FAIL aż operator przygotuje jedną realną blokadę.
Po aktywacji ostatniej części ten sam skrypt z `--expect blocked` potwierdza
checkpoint `20/20 + konflikt + zero lock/signal/rewards/consumption` przed
normalnym rozstrzygnięciem konfliktu.

## 7. Kontrolowany production E2E

Scenariusz obowiązkowy:

```text
19 aktywnych części
+ jedna realna blokada konfliktowa
  -> aktywacja dwudziestej części
  -> network_complete = true
  -> cycle active / conflict blocked
  -> brak locka, signal, rewards i consumption
  -> normalne rozstrzygnięcie konfliktu
  -> automatyczny immutable lock
  -> dokładnie jeden GhostSignal
  -> parts, connections, archive, rewards, territories
  -> globalny Signal Show
  -> hard settlement
  -> stary cycle.closed
  -> dokładnie jeden GhostSystem vNext i next cycle.active
  -> aplikacja rankingu z pierwszym historycznym sygnałem
```

Nie wykonujemy drugiego triggera, ręcznego `UPDATE/INSERT`, ręcznej aktywacji
consumed parts ani ręcznego tworzenia następnego cyklu.

## 8. Postflight

Jeden read-only skrypt, np.:

```text
python scripts/audit_ghostnetwork_endgame.py --cycle-id <id> --strict
```

obsługuje stan `in_progress` i ostatecznie potwierdza:

- jeden lock snapshot i zgodny checksum;
- jeden signal i zgodny checksum payloadu;
- cztery maszyny `5/5` w payloadzie;
- dokładnie po jednym canonical evencie wymaganych typów;
- 20 consumed parts, zero live connections i 20 historical nodes;
- territory plan wykonany dokładnie raz;
- reward ledger, receipts, RSP, statystyki i reputację;
- durable delta delivery do wszystkich audience;
- narrative task -> attempt -> candidate -> receipt -> lifecycle albo jawny,
  dozwolony terminal;
- show session, fazy, login/reconnect evidence i koniec czasu;
- ranking snapshot, checksum i zgodny all-time rebuild;
- przed deadline `stabilizing`, po deadline stary `closed`;
- dokładnie jeden nowy `active` cycle i ponowne dropy.

Postflight zapisuje ID całego lineage: cycle, lock, signal, rewards, events,
publication tasks, show, ranking snapshot i next cycle.

Implementacja: `scripts/audit_ghostnetwork_endgame.py`. Wynik przed końcem show
może być wyłącznie `in_progress`; dopiero zamknięty stary cykl, zakończony show,
applied rewards i dokładnie jeden kolejny aktywny cykl dają `complete`.

## 9. Failure matrix przed GO

| Awaria | Oczekiwane recovery |
| --- | --- |
| konflikt przy 20/20 | active/blocked, zero skutków finału |
| restart przed lockiem | następny tick ponawia readiness |
| restart po locku | `transmitting` auto-resume |
| zły checksum locka | fail-closed |
| crash po signal commit | post-commit sweep, bez drugiego signal |
| crash reward projectora | receipt, brak drugiego RSP |
| crash territory executor | dokończenie immutable planu |
| SQLite locked | bounded backoff, worker online |
| utracona delta | snapshot recovery |
| refresh/login w show | aktualna faza serwera |
| publisher/Ollama offline | gameplay trwa, fallback/retry |
| deadline bez settlement | settlement_blocked, brak vNext |
| dwóch workerów | jeden signal/show/ranking/next cycle |

## 10. Runbook operatora

1. Zamrozić deploye i zapisać HEAD, timestamp oraz PM2 env/status.
2. Wykonać SQLite online backup i sprawdzić możliwość odczytu kopii.
3. Uruchomić strict preflight; archiwizować pełny wynik.
4. Otworzyć bounded monitoring PM2 13, 14, 17 i 18 oraz kolejek.
5. Aktywować ostatnią część wyłącznie realnym gameplay entrypointem.
6. Uruchomić strict preflight z `--expect blocked` i potwierdzić stan complete/
   blocked bez locka i skutków ubocznych.
7. Rozstrzygnąć konflikt normalnym gameplayem.
8. Obserwować jeden lock, signal, consumption plan i show.
9. Sprawdzić klienta live, reload i login drugiego urządzenia.
10. Uruchamiać postflight w trakcie jako `in_progress`.
11. Potwierdzić holder/closer/territory rewards na profilach i w klanie.
12. Po deadline potwierdzić settlement, jeden next cycle i dropy.
13. Potwierdzić ranking v2 oraz rebuild all-time.
14. Nadać `SERVER E2E PASS` tylko przy braku otwartych P0/P1.

Procedura awaryjna:

- `active` bez locka — naprawić blocker, pozwolić workerowi ponowić;
- `transmitting` z poprawnym lockiem — oczekiwać auto-resume;
- `transmitting` bez locka/z błędnym checksumem — stop, backup, analiza;
- `stabilizing` — nie reaktywować części i nie tworzyć cyklu SQL-em;
- brak publikacji — naprawiać task/delivery, nie powtarzać signal;
- brak nagrody — naprawiać projector/receipt, nie dopisywać RSP;
- settlement blocked — zachować stan, znaleźć brakujący receipt, nie omijać gate.
