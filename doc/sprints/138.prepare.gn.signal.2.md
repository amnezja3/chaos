# 138.prepare.gn.signal.2 — GhostSignal Show i cutover GhostSystem vNext

Status: `COMPLETE / SERVER-DEVICE PASS / BLOCKING 138.2 THROUGH .signal.3`

Implementacja canonical (`.2.0-.2.3`) jest gotowa lokalnie. Test produkcyjnego
`20/20` pozostaje zabroniony: środowisko serwerowe korzysta z fixture/test
signal, a ostatnia produkcyjna część pozostaje `public`.

Drugi z trzech sprintów bramki pierwszego GhostSignalu. Implementuje globalne,
serwerowo synchronizowane wydarzenie końca cyklu oraz bezpieczne przejście do
nowej wersji GhostSystemu. Nie uruchamia produkcyjnego `20/20`.

---

## 1. Cel

Istniejące 15-minutowe `stabilizing` zostaje wykorzystane jako canonical okno
`GhostSignal Show`. W tym czasie:

- wszyscy gracze widzą ten sam moment transmisji;
- zwykły gameplay jest zablokowany stanem backendu;
- reload, reconnect i login nie resetują show;
- mechanika finału pozostaje niezależna od UI, SFX i Ollamy;
- GhostSystem vNext jest przygotowany, ale staje się aktywny dopiero po czasie
  show i pełnym settlement.

---

## 2. Stan wejściowy

Obecnie:

- transmisja ustawia `restart_required` i rozpoczyna `stabilizing` na 15 minut;
- viewer snapshot utrwala bezpieczny alias sygnału, wersje i deadline;
- Suite blokuje akcje również po reloadzie;
- PM2 14 po deadline wykonuje hard settlement i rollover;
- wersja GhostSystemu jest jednak zwiększana już podczas transmisji;
- nie istnieje durable show session ani pełnoekranowa reżyseria faz;
- login podczas stabilizacji nie ma kompletnego show cutover;
- stabilizacja jest mechaniką backendową, a nie globalnym wydarzeniem.

---

## 3. Canonical lifecycle show

```text
signal.sent
  -> show session created
  -> cycle.stabilizing
  -> NETWORK LOCK
  -> MACHINE SYNCHRONIZATION
  -> SIGNAL TRANSMISSION
  -> WORLD CONSUMPTION / ARCHIVE
  -> RESULTS / REWARDS
  -> GHOSTSYSTEM RESTART
  -> show_time_elapsed + settlement_complete
  -> old cycle.closed
  -> current_version = next_version
  -> exactly one next cycle.active
```

Show jest projekcją canonical signal/cycle state. Nie jest drugim mechanizmem
finału.

---

## 4. Durable show session

Backend przechowuje co najmniej:

```text
show_id
signal_id
cycle_id
show_started_at
show_ends_at
from_system_version
to_system_version
phase_policy_version
status
```

`show_phase` może być wyliczane deterministycznie z czasu serwera. Jeżeli jest
materializowane, pozostaje projekcją możliwą do odbudowy.

Jedno `signal_id` ma jedną show session. Retry, restart PM2 i dwóch wykonawców
nie mogą przesunąć `show_started_at` ani utworzyć drugiego show.

Docelowy czas startowy: `900 s`, sterowany centralnym configiem.

---

## 5. Fazy prezentacyjne

1. `NETWORK LOCK` — zamknięcie starego świata i pokaz 20 węzłów;
2. `MACHINE SYNCHRONIZATION` — cztery maszyny po pięć części;
3. `SIGNAL TRANSMISSION` — zbudowanie i wysłanie sygnału do 2108;
4. `WORLD CONSUMPTION / ARCHIVE` — części, połączenia i terytoria przechodzą
   do historii;
5. `RESULTS / REWARDS` — uczestnicy, closer, klany i naliczenia;
6. `GHOSTSYSTEM RESTART / BOOT vNEXT` — wygaszenie vN i start vNext.

Dokładny timing faz, assety, copy i SFX są wersjonowaną policy prezentacji.
Nie są zaszyte w losowych timeoutach wielu komponentów.

Fallback show musi działać bez Ollamy. Model może dostarczyć wzbogacenie
narracyjne poza hot path, ale nie wybiera faktów, wyników ani długości faz.

---

## 6. Zachowanie klienta

### Otwarta sesja

Po canonical evencie lub snapshot reconcile klient:

- zamyka zwykły shell gameplay;
- otwiera pełnoekranowy Signal Show;
- blokuje mapę, terminal i write actions;
- odtwarza fazę wynikającą z czasu serwera;
- nie wysyła komendy „zakończ show”.

### Login podczas show

```text
login -> auth -> viewer cycle snapshot -> active show -> właściwa faza show
```

Show zastępuje zwykły preloader. Gracz nie zaczyna własnych 15 minut.

### Rejesteacja podczas show

```text
registry -> viewer cycle snapshot -> active show -> właściwa faza show
```

Show zastępuje zwykły preloader, po ukończeniu rejestracji, gracz jest przekierowany do show. Gracz nie zaczyna własnych 15 minut.


### Refresh i reconnect

- `show_started_at` i `show_ends_at` nie zmieniają się;
- snapshot naprawia utraconą deltę;
- klient wraca do aktualnej fazy;
- System Messaging i SFX nie tworzą duplicate storm.

### Gracz offline przez całe show

Po zakończeniu show dostaje vNext i jednorazową informację o finale. Nie musi
odtwarzać pełnych 15 minut. Z wiadomości może przejść do archiwum/rankingu,
który powstaje w `.signal.3`.

## 7. Viewer-safe kontrakt

Minimalna projekcja:

```text
show_active
signal_public_id
show_started_at
show_ends_at
show_phase
from_system_version
to_system_version
upgrade_pending
restart_required
```

Nie ujawniamy internal signal ID, lock payloadu, prywatnych owners ani danych
spoza audience contract. Live delta i świeży snapshot prowadzą do tego samego
stanu UI.

---

## 8. Cutover wersji

Rozdzielamy wersję przygotowaną od aktywnej:

```text
current_version = N
next_version = N + 1
upgrade_pending = true
```

Transmisja może zapisać `next_version`, ale nie prezentuje go jako działającego
świata. Dopiero:

```text
show_time_elapsed == true
AND settlement_complete == true
```

pozwala wykonać:

```text
old cycle = closed
current_version = N + 1
upgrade_pending = false
one next cycle = active
```

Migracja zachowuje compatibility istniejących `restart_*`,
`stabilization_until`, publikacji i viewer snapshots.

---

## 9. Granice

- frontend nie jest authority czasu ani fazy;
- brak lokalnego 900-sekundowego timera jako źródła prawdy;
- brak nowego workera; PM2 14 obsługuje deadline/settlement;
- brak LLM w mechanicznym hot path;
- UI failure nie powtarza signal/rewards/consumption;
- show nie ładuje heavy profiles ani całego świata;
- payload show korzysta z immutable lock/ranking-ready snapshotu;
- mobile nie renderuje ciężkiej mapy pod pełnoekranowym show;
- SFX respektuje istniejącą magistralę i ustawienia użytkownika;
- aktywne operacje starego świata nie przyjmują write actions.
