## 1. Cel

Doprowadzić istniejący endgame do stanu, w którym:

- kompletna sieć z realnym konfliktem pozostaje bezpiecznie zablokowana;
- rozstrzygnięcie ostatniego konfliktu automatycznie odblokowuje closure;
- lock i GhostSignal powstają dokładnie raz;
- payload zawiera prawidłowe części, maszyny, topologię i closera;
- nagrody są konfigurowalne i projektowane dokładnie raz;
- terytoria uczestniczące w sygnale mają immutable plan konsumpcji;
- wykonanie planu jest idempotentne i recoverable;
- settlement potrafi udowodnić kompletność mechaniki przed rolloverem.

Po tym sprincie system jest mechanicznie gotowy, ale produkcyjny finał nadal
blokują `.signal.2` i `.signal.3`.

## 2. Stan wejściowy (`AS-IS`)

Już działa:

- `GhostNetworkClosureService` i readiness sieci;
- przejście `active -> transmitting` z immutable lock snapshotem;
- jeden `ghost_signals` na cykl;
- konsumpcja 20 części, 20 historical nodes i usunięcie connections;
- reward ledger, receipt po `reward_key`, lease i retry projekcji;
- automatyczne resume `transmitting` przez PM2 14;
- durable endgame delta/narrative repair;
- 15-minutowe `stabilizing` i hard settlement;
- atomowy, idempotentny next-cycle rollover.

Potwierdzone luki:

1. conflict gate closure czyta `ghost_strategic_conflicts`, lecz wymaga
   udowodnienia zgodności z produkcyjnym konfliktem terytorium;
2. lock zapisuje `machine_progress`, a konstruktor payloadu odczytuje
   `machines`; payload może utracić cztery maszyny;
3. finał zapisuje `ghost_signal_node_holder` i `ghost_signal_closer`, podczas
   gdy projekcja statystyk/reputacji zna starsze nazwy
   `transmission_node_held` i `network_closer`;
4. wartości `8 RSP` za node i `20 RSP` dla closera są zaszyte w transmisji;
5. terytoria nie są obecnie konsumowane przez GhostSignal;
6. settlement nie zna jeszcze territory planu;
7. nie istnieje osobny canonical stan `GhostSignal.armed`.

## 3. Decyzja o stanie `20/20 + konflikt`

Nie dodajemy sztucznego persisted `armed` tylko dla nazwy w UI.

Stan canonical:

```text
cycle.status = active

endgame_blocked = true
blocker = unresolved_conflict
lock snapshot = brak
GhostSignal = brak
rewards = brak
consumption = brak
```

W prezentacji można użyć tekstu „sieć uzbrojona” lub „sygnał gotowy”, ale nie
jest to status rekordu GhostSignal. `network_complete` nie oznacza rozpoczęcia
transmisji.

Po rozstrzygnięciu ostatniego konfliktu:

```text
conflict resolved
  -> canonical event lub okresowy tick PM2 14
  -> readiness
  -> immutable lock
  -> transmitting
  -> idempotentny transmission commit
  -> signal.sent + stabilizing
```

Event przyspiesza próbę, natomiast PM2 14 pozostaje recovery authority po
zgubieniu eventu, restarcie lub SQLite contention.

## 4. Zakres implementacji

### 4.1. Canonical conflict resolver

Jedna funkcja jest używana przez readiness, runtime tick, preflight i
postflight.

- realny `pending/active/contested/escalating` — blokuje;
- `resolved/closed` — nie blokuje;
- aktywny `part.conflict_state` bez poprawnego rekordu konfliktu — blokuje
  fail-closed i raportuje niespójność;
- osierocony historyczny rekord bez live conflict i bez aktywnego stanu części
  — nie blokuje wiecznie, lecz tworzy audit warning;
- błąd odczytu authority — blokuje, nigdy nie oznacza „zero konfliktów”.

### 4.2. Immutable lock i payload maszyn

Canonical klucz to `machine_progress`. Lock i sygnał muszą zawierać dokładnie
cztery maszyny, każda z pięcioma aktywnymi częściami i `machine_online=true`.
`machines` może być tylko aliasem compatibility. Pusty fallback blokuje
transmisję przed mechanicznym commitem.

Lock przechowuje co najmniej:

- 20 części z anchor/owner/clan/territory snapshot;
- 20 connections, ring order i topology checksum;
- cztery wpisy `machine_progress`;
- operator contributions i closera;
- konflikty istotne dla części;
- territory consumption plan i reward plan;
- schema version, trigger, `locked_at` i checksum.

Po locku retry nie przelicza wyniku z bieżącego świata.

### 4.3. Reward policy i canonical reward types

Centralna, walidowana polityka steruje:

```text
node_holder_rsp
closer_rsp
territory_consumed_rsp
territory_role_multipliers
clan_reputation_by_reward
```

Migracja zachowuje wartości startowe `8/20`, dopóki balans nie zostanie jawnie
zmieniony.

Canonical typy:

```text
ghost_signal_node_holder
ghost_signal_closer
ghost_signal_territory_consumed
```

Stare nazwy są aliasami wejściowymi. RSP, statystyka profilu i reputacja klanu
muszą rozpoznawać canonical typy. Stabilny reward key opiera się o
`signal_id + reward_type + subject_id + reference_id`.

### 4.4. Immutable territory consumption plan

Do planu trafiają:

1. unikalne primary territories przypisane do 20 części;
2. bezpośrednie terytoria uczestniczące w rozstrzygniętych konfliktach tych
   części;
3. maksymalnie jeden hop rzeczywistego overlapu terytorium tego samego klanu
   z terytorium z punktu 1 lub 2.

Nie ma cross-clan alliance ani rekursywnego pochłaniania całej sieci klanu.
Jedno territory ID jest konsumowane i nagradzane raz.

Primary/conflict territory pozostaje znane po ID mimo wadliwej geometrii.
Jeżeli geometria jest potrzebna wyłącznie do dodatkowego overlapu, taki dodatek
można pominąć z audit warningiem. Błąd nie może rozszerzyć zbioru konsumpcji.

### 4.5. Territory consumption

Stan wykonawczy:

```text
player_areas.status = consumed
ghost_signal_territory_consumptions.signal_id = <signal_id>
ghost_signal_territory_consumptions.consumed_at = <server timestamp>
ghost_signal_territory_consumptions.reason = ghost_signal
```

Consumed territory znika z aktywnej mapy, nie rozszerza się i nie bierze udziału
w nowych konfliktach. Immutable receipt zachowuje właściciela, klan, geometrię,
area, rolę, wersję publikacji i snapshot składowych celów.
Executor używa wyłącznie planu z locka. Crash w połowie pozostawia bezpieczny
retry, a nie ponowne wyliczenie planu.

Nieodwracalna ścieżka ma bezpiecznik
`CHAOS_GHOSTNETWORK_SIGNAL_TERRITORY_CONSUMPTION_ENABLED`. W `.signal.1` ma on
wartość `0`; decyzja jest kopiowana do immutable locka, więc restart ani późniejsza
zmiana environment nie zmieni wyniku zablokowanego już cyklu.

### 4.6. Hard settlement

Settlement potwierdza:

- jeden poprawny lock i signal;
- 20 consumed parts, zero live connections i 20 historical nodes;
- planned territories = consumed territories;
- komplet final reward rows i zakończone projekcje;
- post-commit archive/delta receipts.

Brak dowodu po deadline daje `settlement_blocked`. Nie powstaje vNext.
